## 🤖 AI Guidelines for Enterprise Solution Generation
 
**Document Status:** Canonical / Enforced  
**Audience:** Humans and AI Assistants  
**Applies To:** All AI-assisted generation for this repository

---

## 1. Purpose of This Document
 
This document defines **mandatory rules** for how any AI Assistant may generate, modify, or reason about code, structure, or assets within this enterprise solution.

**The solution structure is frozen.**  
AI is not permitted to redefine, simplify, modernize, or "improve" it.

The purpose of these guidelines is to:
- Ensure long-term **structural stability**
- Support **multiple roles** (DBAs and Application Developers)
- Prevent architectural drift caused by changing AI recommendations
- Enable **consistent, repeatable solution generation**

Any AI output that violates these rules is considered **invalid**.

---

## 2. Canonical Physical Structure Authority (Frozen)

The physical enterprise OS and repository structure is defined **exclusively** in:

```
/Docs/OS-Structure.md
```

This structure is **non-negotiable** and must be followed verbatim.

AI assistants must **not**:
- Redefine the physical structure
- Summarize or restate the structure inline
- Infer alternative layouts

All structural compliance is judged against `/Docs/OS-Structure.md`.

---

## 3. Ownership Model (Critical)
 
This solution is intentionally designed for **multiple specialized teams** working in parallel.

### 3.1 Database Team (DBA Ownership)
 
**Authoritative scope:** `/Databases`

DBAs:
- Work exclusively within `/Databases`
- Do **not** modify `/SRC` or `/UIs`
- Do **not** need to understand application-layer architecture
- Use Visual Studio strictly for database development

Allowed assets:
- SQL projects
- Schema scripts
- Migrations
- Indexes
- ETL scripts
- Stored procedures
- Functions
- Seeds

🚫 AI must **never** generate:
- C# code inside `/Databases`
- Application logic inside database projects

### 3.2 Application Development Team Ownership
 
**Authoritative scope:** `/SRC`, `/UIs`, `/Tests`

Developers:
- Consume database functionality via interfaces and repositories
- Do **not** edit raw database scripts
- Do not bypass Contracts or Infrastructure layers

---

## 4. Layer Definitions and AI Rules

### 4.1 /SRC/Domain — **DDD Core**
 
**Purpose:** Pure domain model

✅ Allowed:
- Entities
- Value Objects
- Domain Events
- Enums
- Domain interfaces

🚫 Forbidden:
- Database code
- EF Core
- SQL
- HTTP
- UI concerns
- Logging frameworks

**AI rule:** Domain must remain persistence-ignorant.

### 4.2 /SRC/Contracts — **Stable Interface Boundary**
 
**Purpose:** Shared API between layers and teams

✅ Allowed:
- DTOs
- Interface contracts
- Shared messages
- Serialization-friendly models

🚫 Forbidden:
- Business logic
- Implementation details
- Infrastructure dependencies

**AI rule:** Changes here must be minimal and deliberate.

### 4.3 /SRC/Infrastructure — **Implementation Details**
 
**Purpose:** Technical implementations of Contracts

✅ Allowed:
- Repository implementations
- Database providers (SQL Server, Postgres, etc.)
- Mappers
- Connection factories
- ORM usage

🚫 Forbidden:
- Business rules
- UI concerns
- Direct database schema definitions

### 4.4 /SRC/Application — **Use Cases & Workflows**
 
**Purpose:** Business orchestration

✅ Allowed:
- Services
- Workflows
- Validation
- Transaction coordination

🚫 Forbidden:
- HTTP concerns
- UI logic
- Direct database access

### 4.5 /SRC/Api — **Delivery Mechanism**
 
**Purpose:** HTTP/REST interface

✅ Allowed:
- Controllers
- Filters
- Middleware
- Dependency injection
- Program / Startup configuration

🚫 Forbidden:
- Business logic
- Direct database logic

---

## 5. /Builds — Enterprise Shared Binaries

The Builds directory contains **precompiled, governed enterprise libraries**.

✅ Characteristics:
- Not NuGet packages
- Not generated by AI
- Not modified per-solution
- Shared across multiple solutions

🚫 AI must **never**:
- Modify binaries
- Recreate Build assets
- Replace Build references with NuGet packages unless explicitly instructed

---

## 6. /UIs — Consumer Applications

UI projects:
- May reference `/SRC`
- Must never bypass Application or API layers
- Must not access Infrastructure or Databases directly

Supported UI types include:
- Web
- Console
- Windows Services
- WPF
- SQL CLR
- Automation tools

---

## 7. AI Usage Rules (Strict)

### ✅ AI IS ALLOWED TO:
- Generate files **within an existing folder**
- Implement a class **defined by an existing interface**
- Generate SQL scripts within a specific database provider folder
- Flesh out services, repositories, controllers **incrementally**
- Generate ONE project or ONE component at a time

### 🚫 AI IS NOT ALLOWED TO:
- Generate a full solution in one pass
- Invent folder structures
- Add or remove projects
- Modify cross-layer dependencies
- Reorganize existing files
- Change architectural intent

---

## 8. Incremental Generation Requirement

All AI-assisted work must be:
- **Incremental**
- **Scoped**
- **Layer-specific**

✅ Correct:
“Generate a SQL Server migration script for adding CustomerStatus."

✅ Correct:
“Generate the repository implementation for ICustomerRepository."

🚫 Incorrect:
“Generate the full enterprise solution."

---

## 9. Enforcement Rule

Any AI-generated output that violates **any rule in this document** or `/Docs/OS-Structure.md` is:
- Invalid
- Must be rejected
- Must not be merged
- Must not be relied upon

**AI correctness is judged by structural compliance first, code quality second.**

---

## 10. Final Principle (Non-Negotiable)

**The architecture belongs to the organization.  
The AI is a tool, not an architect.**

By adhering to this document, AI becomes:
- Predictable
- Reliable
- Useful
- Safe in an enterprise context

**END OF DOCUMENT**
